# SQLite 存储与共享事实（P1–P5）

融资、股东人数、共享日价、财报原始记录、分红事件、估值观察、行业快照及手工财报覆盖均已接入 SQLite。旧 JSON 只在启动时幂等导入，或在没有数据库的兼容路径使用；正常页面和 API 从 SQLite 读取。

## 文件与运行

启动 `app.py` 时，在绑定 HTTP 端口后、开始服务前，自动执行：数据库实例锁 → 结构迁移 → 一致性检查 → 中断任务恢复 → 当日备份。数据库路径为 `data/stock_analysis.sqlite3`，启动日志显示实际 SQLite 版本、journal 模式和结构版本。

结构版本为 4：`001_initial.sql` 建立基础表；`002_shared_data.sql` 增加旧 JSON 导入记录和价格版本租约；`003_p4_facts.sql` 增加财报、分红、估值、行业、手工覆盖及旧月度估值快照，并将旧缓存导入身份扩展为 `(path, dataset)`。`004_financing_compact.sql` 配合事务内 Python 转换精简融资 JSON，保留原值及来源约束。旧迁移文件不得修改，升级必须新增编号迁移。

同一个数据库只支持一个应用实例，不同端口也会受到实例锁保护。锁由操作系统管理，进程退出后自动释放；`.sqlite3.lock` 文件留在磁盘不代表仍被锁住，不需要手动删除。此前已运行的旧版进程没有这把锁，升级后应退出旧进程再启动新版。

本机本轮 Python 3.11.9 加载 SQLite 3.45.1，自动使用 DELETE 模式和短写事务。运行时含已认可的 WAL-reset 修复时自动使用 WAL；手动指定 WAL 而版本不符合要求会明确报错。启动失败会关闭已绑定端口，并释放实例锁。其他电脑应运行 `python -m quarterly_dashboard.storage check` 核验其实际组合。

## 连接、事务与版本

`quarterly_dashboard/storage.py` 的 `Database.connection()` 默认开启只读快照；`write=True` 使用 `BEGIN IMMEDIATE`。各线程创建和关闭自己的连接，启用外键检查、5 秒忙等待和 FULL 同步。连接上下文退出时提交/回滚并关闭，不共享跨线程连接。

迁移 SQL 在一个事务内逐条执行，避免 `executescript` 隐式提交造成半迁移。记录统一换行后的 SQL 内容哈希，Git 的 LF/CRLF 转换不影响跨电脑识别；已有迁移内容改变、未知结构版本、不相关数据库均拒绝访问。后续升级应新增迁移文件，不能改已部署的 `001_initial.sql`。已有结构升级前使用 Backup API 保存迁移前快照。

前复权表保存候选/完成状态：只有候选可写，发布前校验记录数和日期边界；完成后的记录不可逐日修改，活动指针必须对应同股票、来源、口径与覆盖范围的完成版本。零值和负值允许保存。默认保留当前和上一版本，固定读取的旧版本获 5 分钟续租；过期版本明确返回 409。启动恢复清理失败任务的候选版本。

## 更新服务

业务服务使用以下顺序；所有网络请求和来源校验在短事务之外执行：

1. `ensure_instrument()` 取得股票身份，六位代码保留前导零。
2. `start_sync()` 登记请求范围、来源、解析器/口径版本和基准修订号。
3. 获取并验证候选数据。网络失败调用 `fail_sync()`。
4. `complete_sync(run_id, result, write_records)` 在一个事务写事实、成功日志和数据水位。回调只执行本地 SQL。
5. 新记录水位与覆盖必须保留已有历史；另一任务已提交时，本任务被标为 `superseded`，需要重新读取状态后再决策。

可复用的类型是 `SyncKey`、`SyncResult`；字段含义请查看代码。`SyncResult.record_count` 是本次接受的记录数，覆盖范围是提交后的整个有效范围，两者不同。空窗口不能被无条件记录为无数据：已有事实时应由业务层核验并保留状态。首次明确无数据可以提交 `no_data`；已有数据不能被它覆盖。

中断恢复仅在持有实例锁的启动阶段执行，标记遗留 `running` 任务失败、删除其候选价格版本，不修改已成功水位。融资首次全量、后续回看 30 个自然日；已知日期缺失拒绝提交，展示查询最近五个日历年的日度记录，前端默认显示一年；一年和三年按日展示，五年按周展示，余额和股价取当周最后一条记录，净买入按周合计。股东不同来源和人数口径独立入库，价格失败不回滚事实。旧筹码 JSON 按文件路径和哈希幂等导入，原文件与迁移副本保留。

融资结构版本 4 只保存一份完整的 `raw_json`；本次响应中字段的来源默认是行级 `run_id`。`retained_fields_json` 只保存来源实际缺失且历史出现过的字段，格式为 `{"字段":{"value":旧值,"run_id":原任务编号}}`，正常记录为 `{}`。连续缺失保留最初来源；重新返回（包括明确 `null`）移除沿用项。数值列仍供图表查询。`Database.check()` 检查沿用任务是否属于同股票、来源及成功融资同步。

版本 4 升级前自动保存 `backups/pre-migration-*.sqlite3`；转换、校验、表替换和版本登记同一事务提交，无法重建旧字段或沿用来源无效时回滚。恢复表原有索引和来源触发器。当前原始响应内字段的旧来源标记冲突写入 `backups/financing-migration-audit-*.json`；审计文件注明提交前验证阶段，以数据库版本记录判断迁移是否提交。升级后需要停服持锁执行 `VACUUM` 才能回收文件空间，本机已完成。[融资精简验收](data-sources/financing-compaction-acceptance.md)

融资的 30 天回看以最后成功数据水位为起点，覆盖至本次日期；两个月未访问会补齐整个缺口。到期的 30 天全量核查会取全部可用历史，失败仍保留旧事实和水位。

共享价格首次拉取完整历史；前复权后续核对至少 20 个已有交易日和两个旧锚点，发现变化或 30 天到期则全量重建。无变化不创建版本，有新日期时在数据库内复制历史并追加。分页重叠与复权基准由来源适配器校验，失败保留有效版本。财务、估值、股东和融资取价通过同一服务；市值及股息率使用不复权价格。

P4 财报每类独立同步：首次分页获取完整可用历史，普通更新每类最近 8 期，离线较久继续分页直到覆盖已有尾部，30 天做全量审计。来源 000001 的 1989/1990 年利润表确实缺少营收，保存原始稀疏记录并提示缺失，近期 8 期缺少必要字段仍拒绝提交；已保存字段在来源中消失也拒绝覆盖。计算时合并已提交事实、旧缓存与手工覆盖，显式 `0` 和 `null` 均保留。

分红首次获取全部事件，普通更新分别按公告日和除权日回看 30 天，并复查未完成预案。来源按报告期精确筛选可能返回空结果；此时记录原因并对该股票执行全量补偿。只有已实施现金事件参与收益计算；财务图与估值股息率共用事件事实和共享不复权价格。

估值首次对 PE、PB、市值各取近十年、近五年、近三年三个窗口，保存各日期的最细真实观察；普通更新各取近一年。长期离线会扩大窗口，30 天核查。日、周、月只是读取聚合，不重复抓取或保存三份。三年及以内自动日度、五年周度、十年月度，早期稀疏点不插值。PS 在每个市值观察日关联当时已披露的收入 TTM。旧 JSON 的月度结果另存旧口径快照，不冒充日度事实。

三个 P4 服务的成功同步会刷新当天 Backup API 备份；来源失败不删除已保存事实或推进该数据集水位。部分数据集成功、部分失败时，成功事实可读，警告指明失败部分。

## 维护命令

这些命令只依赖标准库，可在仓库根目录执行：

```powershell
# 初始化；应用运行时实例锁会拒绝同时执行结构迁移。
python -m quarterly_dashboard.storage init

# 核验结构、完整性、外键、成功日志及活动价格版本的关系。
python -m quarterly_dashboard.storage check

# 在线一致备份，输出必须是新文件，不能覆盖已有备份。
python -m quarterly_dashboard.storage backup --output data/backups/manual-2026-09-30.sqlite3

# 恢复到新路径进行检查，不覆盖当前数据库。
python -m quarterly_dashboard.storage restore --database data/backups/manual-2026-09-30.sqlite3 --output data/verification/restored.sqlite3
python -m quarterly_dashboard.storage check --database data/verification/restored.sqlite3
```

使用恢复库替换正式库前，应停止应用并保存正式库的备份；初版维护工具故意只提供“恢复到新文件”，没有直接覆盖活动库的命令。

备份通过 SQLite Online Backup API 获取快照，验证后发布为自包含 DELETE 模式文件。为避免并发覆盖，发布使用本地文件系统硬链接，当前 Windows NTFS 已实际验证；文件系统不支持硬链接时命令会报错，不声称备份成功。数据库和备份都应放本地磁盘。[SQLite 备份 API](https://www.sqlite.org/backup.html)

启动时生成当天 UTC 日期的首份备份；成功业务更新后刷新当天备份，保留最近 7 份本库命名的日备份。手工备份和迁移前备份不进入此轮转。不要直接复制正在运行的 `.sqlite3`，也不要将活动库和 WAL 文件通过 Git 同步。

## 验证与限制

2026-09-30 的 P4/P5 本机回归包括来源分页/窗口、三类事实服务、迁移/幂等导入、旧数据保留、前端频率切换、异常回滚、并发读取和备份恢复。运行 `python -m pytest -q` 与 `git diff --check` 可复核当前代码；代表股票的冷暖请求参数和响应体大小见 [P4 实测记录](data-sources/p4-acceptance.md)。

同步来的数据库（结构版本 2）完整性检查通过：融资 7,198 条、股东 304 条、601919 不复权日价 4,497 条和前复权版本 1 的 4,498 条。2026-09-30 真实增量核对：前复权 20 个已有交易日和两个旧锚点一致，不复权核对 30 个交易日；未重建版本。业务数据备份恢复后，记录数、活动版本和同步状态逐项一致。本地 8768 服务的页面与接口返回成功，股东、融资响应均固定价格版本 1。

P4 在运行库的隔离 Backup API 副本上验证，不直接升级现有结构版本 2 的运行库。当前本机 Python 3.11.9 / SQLite 3.45.1 只验证 DELETE journal；修复版 SQLite 的真实 WAL 并发与恢复、另一台电脑的启动/恢复尚未完成。当前冷暖测量仅覆盖本机缓存 HTML 生成及三只股票的 P4 来源请求，不能代表整个浏览器页面和所有异步接口。
