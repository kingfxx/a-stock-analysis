# SQLite 存储基础（P1）

当前阶段：基础设施已接入启动，业务加载器仍读写原 JSON。数据库建好不代表融资、财务或价格已经迁入；业务迁移从 P2 开始。

## 文件与运行

启动 `app.py` 时，在绑定 HTTP 端口后、开始服务前，自动执行：数据库实例锁 → 结构迁移 → 一致性检查 → 中断任务恢复 → 当日备份。数据库路径为 `data/stock_analysis.sqlite3`，启动日志显示实际 SQLite 版本、journal 模式和结构版本。

初始结构版本为 1，包含股票身份、融资日表、股东观察、不复权日价、前复权版本/日价、同步状态/运行日志及结构迁移历史，共 9 张表。源适配与业务服务尚未接入这些表，因此目前通常只有迁移历史记录。

同一个数据库只支持一个应用实例，不同端口也会受到实例锁保护。锁由操作系统管理，进程退出后自动释放；`.sqlite3.lock` 文件留在磁盘不代表仍被锁住，不需要手动删除。此前已运行的旧版进程没有这把锁，升级后应退出旧进程再启动新版。

本机 Python 3.10.0 加载 SQLite 3.35.5，自动使用 DELETE 模式和短写事务。运行时含已认可的 WAL-reset 修复时自动使用 WAL；手动指定 WAL 而版本不符合要求会明确报错，不降级伪装成功。启动失败会关闭已绑定端口，并释放实例锁。

## 连接、事务与版本

`quarterly_dashboard/storage.py` 的 `Database.connection()` 默认开启只读快照；`write=True` 使用 `BEGIN IMMEDIATE`。各线程创建和关闭自己的连接，启用外键检查、5 秒忙等待和 FULL 同步。连接上下文退出时提交/回滚并关闭，不共享跨线程连接。

迁移 SQL 在一个事务内逐条执行，避免 `executescript` 隐式提交造成半迁移。记录统一换行后的 SQL 内容哈希，Git 的 LF/CRLF 转换不影响跨电脑识别；已有迁移内容改变、未知结构版本、不相关数据库均拒绝访问。后续升级应新增迁移文件，不能改已部署的 `001_initial.sql`。已有结构升级前使用 Backup API 保存迁移前快照。

前复权表保存候选/完成状态：只有候选可写，发布前校验记录数和日期边界；完成后的记录不可逐日修改，活动指针必须对应同股票、来源、口径与覆盖范围的完成版本。零值和负值允许保存。淘汰时删除未被状态引用的整个版本，不删除完成版本中的单行。抓取、价格比较、版本保留政策、图表固定版本等功能留到 P3。

## 更新服务接入方式

后续业务服务使用以下顺序；所有网络请求和来源校验在短事务之外执行：

1. `ensure_instrument()` 取得股票身份，六位代码保留前导零。
2. `start_sync()` 登记请求范围、来源、解析器/口径版本和基准修订号。
3. 获取并验证候选数据。网络失败调用 `fail_sync()`。
4. `complete_sync(run_id, result, write_records)` 在一个事务写事实、成功日志和数据水位。回调只执行本地 SQL。
5. 新记录水位与覆盖必须保留已有历史；另一任务已提交时，本任务被标为 `superseded`，需要重新读取状态后再决策。

可复用的类型是 `SyncKey`、`SyncResult`；字段含义请查看代码。`SyncResult.record_count` 是本次接受的记录数，覆盖范围是提交后的整个有效范围，两者不同。空窗口不能被无条件记录为无数据：已有事实时应由业务层核验并保留状态。首次明确无数据可以提交 `no_data`；已有数据不能被它覆盖。

中断恢复仅在持有实例锁的启动阶段执行，标记遗留 `running` 任务失败，不修改已成功水位。融资窗口更新、股东口径选择、来源字段合并及旧 JSON 导入规则属于 P2/P3 的业务服务，基础层不替代这些校验。

## 维护命令

这些命令只依赖标准库，可在仓库根目录执行：

```powershell
# 初始化；应用运行时实例锁会拒绝同时执行结构迁移。
python -m quarterly_dashboard.storage init

# 核验结构、完整性、外键、成功日志及活动价格版本的关系。
python -m quarterly_dashboard.storage check

# 在线一致备份，输出必须是新文件，不能覆盖已有备份。
python -m quarterly_dashboard.storage backup --output data/backups/manual-2026-09-30.sqlite3

# 恢复到新路径进行检查，不覆盖当前数据库。
python -m quarterly_dashboard.storage restore --database data/backups/manual-2026-09-30.sqlite3 --output data/verification/restored.sqlite3
python -m quarterly_dashboard.storage check --database data/verification/restored.sqlite3
```

使用恢复库替换正式库前，应停止应用并保存正式库的备份；初版维护工具故意只提供“恢复到新文件”，没有直接覆盖活动库的命令。

备份通过 SQLite Online Backup API 获取快照，验证后发布为自包含 DELETE 模式文件。为避免并发覆盖，发布使用本地文件系统硬链接，当前 Windows NTFS 已实际验证；文件系统不支持硬链接时命令会报错，不声称备份成功。数据库和备份都应放本地磁盘。[SQLite 备份 API](https://www.sqlite.org/backup.html)

启动时生成当天 UTC 日期的首份备份，同日重启复用这份已验证备份，保留最近 7 份本库命名的日备份；手工备份和迁移前备份不进入此轮转。它不是每次业务更新后的备份，后续接入业务写入时再完善备份触发时机。不要直接复制正在运行的 `.sqlite3`，也不要将活动库和 WAL 文件通过 Git 同步。
