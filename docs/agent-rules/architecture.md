# 代码职责与依赖规则

本文件是根 AGENTS.md 的必读补充。新增／修改代码、模块拆分及重构前阅读。目标是让新功能沿明确边界扩展，避免 server 或其他公共文件再次集中全部业务。

## 新功能的归属

编写开发计划前必须阅读本规则及当前代码导航，核对实际入口、相关模块、调用链和已有可复用能力，不能仅凭旧计划或历史架构说明确定设计。计划中明确拟修改／新增模块及其职责、依赖方向和状态所有者；无需新层级或常驻状态时直接说明，不为满足格式增加抽象。

实施前再次对照当前代码复核上述归属，尤其检查复用模块的传递依赖、初始化／恢复链及已有缓存、锁和调度器。跨对话、代码已变化或任务范围调整时，先更新原计划的相关设计与决策，再实施；发现职责边界冲突在本任务范围内解决，不沿用已失效的设计，也不借机扩大为无关重构。

动手前确认已有模块和调用链，复用所属领域；在当前计划中记明路由、业务、来源、解析／计算及运行状态的归属，不强制每个简单修改新建目录或层级。实际目录导航见 [后端代码导航](../../stock_analysis/README.md) 与 [架构说明](../architecture-design.md)。

| 职责 | 位置与约束 |
|---|---|
| HTTP 协议、统一鉴权、恢复门禁、启动入口 | `http/server.py`；不得新增领域业务分支、SQL、缓存合并、指标计算或来源编排 |
| 路径匹配、请求参数／体校验、领域调用、状态码及响应头 | `http/routes/` 的具体功能模块；新增功能先找所属路由组，处理方法须唯一，不得通过同名方法覆盖其他入口 |
| 业务流程、查询、刷新、缓存兼容与数据组装 | 相应 `domains/<领域>/`；新功能有独立流程时建具体模块，不默认扩充 `domains/stocks/data_service.py` 或跨领域公共文件 |
| 配置传入、服务创建及复用、初始化、恢复与清理 | `application.py`，生命周期循环沿用 `runtime.py`；不在组装层堆业务规则或数据处理 |
| 来源请求、分页、跨响应验证与恢复回调 | 所属领域的来源适配模块；复用公共采集入口、预算、锁和证据，不把网络控制搬进纯解析器 |
| 字段解析、格式转换、纯校验和计算 | 领域内的解析／计算模块；显式接收输入并返回结果，不请求、不读写数据库／业务文件、不启动任务或模型 |
| HTML 模板、转义和插值 | `http/rendering.py` 或具体展示模块；业务数据先在领域准备，领域层不拼 HTML 或操作 Handler |

路由应保持「解析请求 → 调用领域能力 → 返回响应」。已有领域读取函数可以直接复用，不强制增加无实际用途的 service/repository/model 层。复杂查询、数据分类合并、公式及刷新流程不写进路由。

## 依赖与状态

- 依赖由 HTTP 指向领域能力，来源适配调用纯解析。领域模块不得导入 HTTP 或 application；应用组装通过显式配置／依赖创建服务，不让业务反向取得 Handler 或 server 全局变量。
- 纯解析／计算不得引入 requests、SQLite、采集器或 HTTP 依赖，也不能通过间接调用绕过上述限制。
- 缓存、锁、调度器及服务实例各有唯一所有者；新模块复用已有实例和恢复清理链，不复制状态或另起调度器。数据库／目录配置显式传入，不能依赖模块层级固定 parent 数或硬编码个人路径。
- 公共模块只容纳已有明确共享职责。不新建无用途的 utils/core、大型函数注册表、全局代理或通用插件框架；不把原单体换名迁入 application、data_service 或 context 后继续扩充。
- 拆分后生产调用指向真实归属。确有调用者需要兼容导出时记录对象和理由，避免永久双份实现、sys.modules 别名、动态转发或反向导入维持旧耦合。

## 控制增长

- 每次增量都检查受影响文件是否出现第二类独立职责。出现时，在本任务范围内先提取该职责，再加入新功能；无关旧问题另记，不借机全仓重写。
- 行数增长是检查信号，不设机械行数门槛。按真实依赖、修改原因和独立验证能力确定拆分；不为减少行数压缩代码，也不提前建立空模块。
- 应用组装文件、现有数据服务和具体路由组同样遵守此规则，不能因其已经命名为 service/routes 而无限承接新功能。

## 验证与交付

- 开发计划及实施前按真实依赖记录受影响路径、拟执行检查及选择理由；简单修改直接简述，不为测试规划另建流程。默认选择能验证本次行为与关键风险的最小范围，不把「运行全量套件」当作每项开发的固定步骤。
- 文档、注释及简单文案／样式调整只做差异、语法或必要页面检查；无运行逻辑变化不跑后端套件。局部计算／接口／交互变更运行对应测试和必要的相邻回归；修复缺陷优先验证具体复现及修复后的行为。不为可逆低影响修改编写与实现逐句对应的测试。
- 共享协议、鉴权、数据发布、服务状态或生命周期等变更，按实际调用者扩大到相关集成路径；只有影响确实广泛、涉及全路由／大范围重构，或无法可靠界定回归范围时才运行全量，并在计划或进度中说明具体原因。用户明确要求完整验收时按授权执行。
- 相关检查通过后继续交付，不无故扩大或重复；只有新增改动、检查失败或尚未排除的具体风险才追加。失败先定位，修复后复测失败项及受修复影响的路径；沙箱／端口／浏览器等环境阻碍只重跑受阻检查。保留既有有效断言，不通过删断言、放宽验收或随意跳过来控制成本；结果说明实际范围与剩余限制。
- 保持 URL/API、参数默认、状态码／响应头、鉴权、异常边界、财务口径、刷新授权、缓存版本、来源证据及初始化／恢复顺序；需要改变行为时在计划中明确，不能包装成纯搬动。
- 更新测试的导入与 monkeypatch 到真实调用点，保留原断言和隔离策略；不能靠新模块回调 server、吞异常、跳过测试或削弱断言让拆分通过。
- 修改 HTTP／来源边界时运行受影响的相关回归，按需选择 `tests/test_http_source_boundaries.py` 中独立解析、实例隔离、脚本转义、门禁及路由重名检查，不因仅修改前端展示就重复整组。边界发生新增或变化时补充相应测试；纯解析使用离线输入，不靠真实请求验证。
- 需要扩大验证的重构，先记录相应范围的当前基线，再执行选定回归及必要的宿主机 8765 验收；全量条件按上文判断，不仅凭修改了共享文件就一律全量。只改文档不启动测试服务或重启后台。
- 交付检查领域反向依赖、纯模块的网络／数据库依赖、路由重名和重复状态，更新实际架构导航与当前计划。现有测试只覆盖已实现检查；不得将尚未建立的全仓依赖扫描或 CI 描述为已有保障。
