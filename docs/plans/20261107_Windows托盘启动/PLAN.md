## 目标与授权

用户已选定“无黑窗启动、托盘常驻、浏览器打开页面”，并于 2026-11-07 明确要求执行。授权实施、必要依赖安装、局部测试、快捷方式创建及安全切换宿主机 8765 后台。实施与验收沿用本目录的 PLAN.md、DECISIONS.md、PROGRESS.md。

## 已核对的当前结构

1. `start_dashboard.bat` 选择解释器、检查依赖，前台运行 `app.py --open-browser`；现有批处理本身会显示命令行窗口。
2. `app.py` 解析 `--port` 和 `--open-browser`，调用 `http/server.py::serve()` → `runtime.py::run_server()`。
3. `run_server()` 拥有 HTTP 服务、唯一 Scheduler、数据库恢复循环和空闲内存回收实例。在数据库锁内绑定本机地址、初始化应用、启动 Scheduler，再进入 `serve_forever()`；目前通过 KeyboardInterrupt 进入退出清理。
4. `infrastructure/storage.py::instance_lock()` 按数据库路径持有操作系统文件锁，防止第二个后台或维护实例使用同一数据库；持久锁文件存在不等于进程仍在运行。恢复循环每轮释放并重新获取该锁。
5. `application.py::_initialize_runtime()` 负责数据库初始化、中断恢复、备份及旧缓存导入；`_clear_runtime_services()` 负责恢复后的服务缓存重建。桌面层不能复制这套逻辑。
6. `application.py::_restore_activity()` 已检查公共采集运行状态及行业/AI 内存工作线程，但不能据此直接宣称已覆盖所有维护任务。退出设计还需核对维护、归档、恢复发布、同步请求等实际活动及其门禁。
7. `Scheduler.close()` 已停止调度、请求部分任务取消并等待；存在超时抛错路径，不能把“调用 close”视为所有任务均已安全退出。
8. `RequestGate` 已用于请求和后台调度准入；恢复发布会关闭监听、执行恢复再创建新服务实例。桌面控制应跟随新实例更新，不能永久保存旧 server 引用。
9. 日常日志主要为 print 和 HTTP 标准错误输出；`pythonw.exe` 下标准流可能为空，需要在导入业务模块之前建立日志输出。
10. `paths.py` 和 AppSettings 提供原项目、数据库和缓存路径；快捷方式启动不能依赖当前工作目录。`stock_search.py` 用 `sys.executable` 执行带输入输出管道的短命拼音工作进程，需要覆盖 pythonw 环境兼容性。

已查阅架构规则、后端代码导航及相关实现；未发现同目标计划。此前内存优化计划属于独立目标，本任务不在其目录维护状态。

## 生命周期与退出约束

- 生命周期至少区分启动中、运行中、恢复中、退出中、失败/已停止；菜单状态以 runtime 的线程安全快照为准。
- 就绪通知须在应用初始化及调度初始化完成、HTTP 可处理请求后发生，避免当前“绑定端口即就绪”的误判。等待与通知均可取消，不在托盘线程中执行耗时初始化。
- HTTP shutdown 必须由非 `serve_forever()` 所在线程调用，并处理尚未进入循环、初始化失败、反复点击退出、恢复重建 server 时的竞态，避免死锁。
- 退出前先核对实际活动和原门禁语义。空闲判定与阻止新任务准入必须协调，不能“先查空闲，再无保护关闭”。等待中的读请求允许完成；有业务任务则保持运行并给出说明。恢复发布/维护关键区禁止中途退出。
- 对无法安全停止的状态不使用 os._exit、TerminateProcess 或 daemon 线程随主线程直接退出；失败和超时可见、可追踪，未确认清理完成不得显示退出成功。
- 正常顺序为停止接收新工作、排空请求/活动、停止调度、关闭 HTTP 与其他已有资源、释放数据库锁，再清理托盘、激活等待器、Win32 句柄及日志。按实际资源依赖细化顺序，并覆盖 cleanup 抛错时其余资源的释放。
- 保持恢复时的原初始化/跳过 legacy 顺序；恢复过程中托盘不消失、不重复打开浏览器、不新增 Scheduler。停止请求与恢复互斥关系须有回归证明。
- 首版不保证系统强制关机/结束任务时能无限等待业务完成；正常桌面退出不能依赖强杀。异常中断仍沿用现有启动恢复。

1. 双击快捷方式全程无黑窗（含拼音等短命子进程），只有一个后台、一个 Scheduler 和一个托盘图标。

### 内存验收

- 使用同一解释器、原数据库、相同页面访问与任务状态，顺序对比 CLI 与托盘；每种方式只运行一个实例。
- 分别记录初始化完成稳定后的空闲、浏览同一页面后关闭页面、空闲回收后的状态；记录采样时刻和后台活动，至少三次短间隔采样报告中位数。
- 记录进程 Working Set 和 Private Bytes；若依赖受限，明确实际可用指标。不把共享页工作集简单相加等同于独占内存。
- 浏览器相关进程独立列出，避免将页面开关造成的差异算到托盘；关闭页面和隐藏窗口不被描述为已释放后台内存。
- 第一版目标为只增加托盘/日志/激活控制所需开销，不引入第二个常驻 Python 或网页引擎。以空闲 Private Bytes 增量约 30 MiB 以内作为初步调查线：超出需定位依赖和状态差异并说明，不能当作已测承诺或硬性平台保证。
- 不通过强制压缩工作集、删除业务缓存或改变现有一小时空闲回收策略制造低内存数字。
