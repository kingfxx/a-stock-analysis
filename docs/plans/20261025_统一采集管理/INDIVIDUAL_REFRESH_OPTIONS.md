# 个股刷新入口方案分析（历史讨论）

2026-10-27状态：用户已确认取消页面到期自动采集，保留单股手动/全量，首次新股自动全量初始化，按组配置定时；公共管理页只设一个个股模块。存储仍沿用既有业务表和metadata_only，仅增加必要管理元数据。实施计划见[PLAN](PLAN.md#2026-10-27追加个股采集统一管理)，决策及当前进度见DECISIONS.md、PROGRESS.md。以下是历史候选方案，不再作为当前实施指令；2026-10-27已实施并完成原8765只读验收。

当前只统一批量采集入口，个股普通刷新、全量刷新和已授权到期自动检查保持现状；此文是分析，不代表已获授权迁移。

|方案|研究股票时的操作|集中管理能力|适合情况|
|---|---|---|---|
|个股入口全部保留|当前股票页直接刷新，最方便|批量和个股入口分散，需另外补统一状态|优先维持现有使用习惯|
|全部移入采集管理|需要跳转并确认股票与数据范围；可预填代码减轻负担|确认、历史、失败恢复入口集中|更重视运维和批量管控，能接受切换页面|
|分层处理（建议）|普通刷新留在股票页；全量刷新跳转管理并预填当前股票|重型操作集中，日常研究仍顺手|兼顾研究效率和任务可追踪性|

建议把普通刷新理解为“更新当前研究对象”，保留上下文；把全量刷新理解为较重的历史核对/重新获取，后续移到采集管理，明确单只股票、数据项与模式。也可以先保留普通按钮但让它仅导航到预填当前代码的管理页，代价是每次刷新多一次跳转。

个股到期检查属于独立授权的自动策略，是否搬按钮不应顺带改变它：仍只在已关注股票及现有到期/失败抑制规则内触发，不扩大股票范围，不自动创建全市场个股定时。

技术上，个股一次刷新包含财务、估值、行情、股东人数、融资等多个数据同步子任务，目前真实记录是多个sync_runs；不像指数那样天然有一个operation覆盖整次操作。若迁入统一管理，应设计一次用户操作与这些子任务的轻量关联、明确实际支持的取消/恢复，再适配现有采集器。不能只增加一个“个股刷新”按钮就声称已有统一总进度，也不应复制原始响应或重写旧历史。

建议后续确认三个点后单独实施：保留普通刷新还是改为跳转；全量刷新是否只允许单股；管理页需要哪些数据项和真实进度。正式财报准备与模型生成保持独立，不能归入普通采集自动执行。
