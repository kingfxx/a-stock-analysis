# 一次性补齐 2016—2018 年季度末总市值

## 目标与边界

补齐行业对比所需的 **2016Q1—2018Q4** 季度末公司总市值，共最多 12 期。2018 年已有东方财富有效数据应保留，只补缺失的股票／日期组合。

- 不采集更早年份，不增加日度历史市值业务，不修改常规集采按钮或定期更新流程。
- 使用独立、可断点续跑的一次性工具；最终写入现有市值体系，不新建业务表。
- 保持现有行业成员、分类及冻结名单口径，不把“当前成员回溯”改称“历史全市场”。
- 先采集、计算、核对，再备份和导入，最后验收页面。保留来源响应和验收报告，不生成长期 baseline JSON。
- 本文保留原始执行计划；2026-10-09 已完成一次性补采与导入，实际结果见文末执行记录及专项来源说明。

## 阶段一：盘点真正的缺口

1. 检查工作区已有修改，避免覆盖、混入其他任务的代码；不自动 commit/push。
2. 只读查询日常 `data/stock_analysis.sqlite3`，按当前实际活动／成功批次规则读取市值，不简单把任意旧批次当作有效数据。
3. 列出 12 个季度、季度末自然日、最后市场交易日、冻结名单、应有公司数、已有有效公司数和缺失数。
4. 优先复用 `sw_cap_quarter_rosters` 和 `sw_cap_quarter_members`；缺名单时沿用项目现有冻结名单机制。复用现有上市日期筛选，上市前期间列为不适用，不用未来公司抬高缺失数。
5. 使用现有交易日资料／日历确认最后市场交易日，不凭周末规则推断节假日，不擅自修改已有季度目标日期。
6. 仅为有缺口的公司和季度安排任务。生成盘点报告，记录运行时实际数目。

## 阶段二：一次性采集与计算

实现独立 CLI 工具，例如 `data/verification/tools/backfill_market_cap_2016_2018.py`。工具须分别提供采集、核对和导入入口，支持断点续跑；默认不写日常库。具体命令以最终实现的帮助输出为准，本文不假设已有命令。

### 股价

- 从 BigQuant 一次或按年度分批查询目标交易日的 `date, instrument, close`，同时提供 SQL 日期条件和 `filters` 日期分区范围。
- 只取需要的股票和日期，保存原始返回及查询参数。不要下载全市场多年每日全部字段。
- BigQuant 空值不能当零，也不能直接认定为停牌。对缺口先查本地腾讯精确日期，再按需请求腾讯未复权历史窗口核对。
- 若精确日期无价格，只有在查明停牌／无成交情况、确认原有系统允许沿用最近实际收盘价时，才使用之前的有效收盘价；保留真实价格日期及沿用理由。来源异常、长期缺失或状态不明则留空，不无限向前找价。
- 不把前复权、后复权价格用于市值，不把腾讯历史响应附带的最新 `qt` 市值当作历史市值。

### 总股本

- 巨潮按股票串行采集完整必要历史，默认可从 1990-01-01 查询至 2018-12-31，以覆盖 2016 年以前最后一条有效股本记录；采集更早股本是查找起始状态，不扩大市值目标年份。
- 每只股票一次取多年的变动记录，建议保持至少约 1 秒请求间隔。复用连接，设超时、有限重试；401／403／429 等返回明确记录，不高频反复请求。
- 保留 `SECCODE`、`VARYDATE`、`DECLAREDATE`、`F003N`、变动原因以及股本结构字段。检查响应 `total/count` 与实际记录数，发现截断时按时间段拆分，不能把截断当作完整历史。
- 以目标市场交易日为股本匹配时点，选该日及以前适用的最近有效记录。不要取之后的股本，不用最新股本回填所有年份。
- 同日多条记录不简单按返回顺序覆盖，核对公告日期、原因及是否修订；冲突不能判定时列为异常。
- 用 Decimal 按 **`F003N × 10,000`** 从万股换算股，保留原始值。缺值或无效值不转零。
- 股本记录既有事件，也可能有财报统计快照；此任务用于事后历史数据补全，不宣称它是当时已知的无前视偏差回测数据。
- 对巨潮缺口才尝试通达信／BaoStock。记录精度、有效时点及回退来源，无法确定适用总股本时留空。

### 市值计算与来源

**总市值（元）= 历史未复权收盘价（元／股）× 对应时点总股本（股）。**

对 A/H、A/B 等多股类公司，先与现有东方财富口径核对：总股本乘 A 股价不等于各市场分别估值后相加。不悄悄变更口径，不使用流通股本代替总股本。

每条待导入结果保留：股票代码、季度、目标交易日、价格实际日期、原价、股本变动日期、公告日期、原始万股值、股数、计算市值、来源字段、方法、原始文件路径及 SHA256、回退说明和核对结果。

可将原始样本路径及哈希放在共享清单／来源引用中，避免逐行重复嵌入大段来源信息。导入统一使用 `sw_cap_provenance` 和 `provenance_id`，事实行 `provenance_json` 沿用兼容占位。

## 阶段三：核对与导入

1. 先生成候选文件、异常清单、季度覆盖率和来源分布；这是运行暂存及验收资料，不是长期 baseline。
2. 抽样覆盖普通公司、A/H 公司、增发、送转／拆并股、回购、上市较晚、停牌及缺口回退公司。
3. 在 2018 年已有东方财富的重叠期做独立核对，新增候选不要覆盖这些有效原值。超过纯显示舍入或已识别协议精度的差异应定位原因，不能仅靠宽容阈值全部放行。
4. 所有可计算结果必须有正值、唯一键、正确日期与可追溯证据。无法解决的缺口明确保留，不伪造“全部补齐”。
5. 使用隔离的临时 SQLite／备份副本演练发布，确认页面读取会选中新批次且原有成员和市值仍然可读。不要只直接 INSERT 几行而漏掉批次、汇总和活动版本关系。
6. 导入前使用项目正式备份机制／SQLite backup API 备份日常库，不裸复制正在写入的主文件而遗漏 WAL。
7. 沿用现有 `sw_imports` 等批次机制，将缺失项及其来源写入 `sw_cap_facts`／`sw_cap_provenance`，按实际发布方式保留已知值并刷新对应季度行业汇总。只处理本次范围。
8. 涉及 `sw_industry_cap_quarters` 时沿用 `expected_count`、`known_count`、`known_cap`、`total_cap` 的现有完整性规则：部分覆盖不能伪装成完整行业总市值。
9. 导入前再次检查当前缺口，避免把采集期间其他更新已补入的数据覆盖；采用事务和幂等规则。中断后重跑只处理未完成内容。
10. 计划阶段已获用户同意“独立工具、核对、备份、补缺”；新窗口收到执行指令后可在此范围内完成，不添加未被要求的常规采集功能。

## 阶段四：验收与整理

- 报告逐季度：应有数、原已有数、新增数、仍缺数、来源分布及异常原因。
- 对原有效市值、其他年份、行业名单及财务数据做前后校验，证明未发生无关改写。
- 验证行业内公司对比、行业汇总和排行在目标期能读取新增市值，且部分覆盖仍显示正确完整性状态。
- 日常验收使用 8765 原后台。若只是独立工具和数据库导入，先检查现有缓存失效机制；需要重启才能生效时，按 AGENTS.md 核对进程并重启 8765，不启动持续运行的测试后台。
- 执行后同步更新相关存储／来源文档，注明 2016—2018 缺口采用计算市值及实际覆盖范围，不宣称数据源直接返回市值。
- 删除已过期的测试库、一次性中间文件及预览缓存；保留原始来源响应、正式备份、可复用工具和最终验收报告。不要删除其他任务资料。
- 失败时报告已完成与未完成部分。若需回滚，仅按本次批次和来源关系处理并核对引用，不覆盖采集期间新增的其他业务数据。
