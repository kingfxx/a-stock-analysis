# 融资存储精简方案

实施状态：2026-10-01 已完成，主库升级版本 4 并整理空间，详见 [验收记录](../data-sources/financing-compaction-acceptance.md)。

日期：2026-10-01。状态：方案待实施。本轮只读检查运行库并编写方案，后台继续运行。

## 目标与结论

融资表继续保存逐日数值和最近一次成功入库的原始响应，将两份完整数据 JSON 和逐字段来源映射，精简为 **一份原始响应＋一份稀疏的沿用字段记录**。

保留近期回看和历史修订能力。普通增量从成功水位向前回看 30 个自然日；同日期覆盖更新，新增日期插入；已有日期缺失、必要字段缺失及请求失败的保护继续有效。精简存储不需要将同步改成只追加新日期。

推荐第一阶段使用可读的 JSON 文本，不增加压缩依赖或新明细表。正常记录只有一份完整 JSON，沿用记录默认为 `{}`。

## 字段设计

保留主键 `(instrument_id, source, trade_date)`，保留融资余额、融券余额、融资融券余额、融资净买入、收盘价等数值列，以及 `content_hash`、`obtained_at` 和 `run_id`。

| 字段 | 新含义 |
| --- | --- |
| `raw_json` | 最近一次成功入库的该日期原始来源记录，保持来源字段和值，不混入沿用值 |
| `retained_fields_json` | 当前原始响应缺少、但此前已有的字段，以及它们最后被来源实际返回时的任务编号；没有沿用字段时为 `{}` |
| `run_id` | 该行当前原始响应所属的成功同步任务；原始响应内字段的来源默认使用这个编号 |
| 数值列 | 供图表直接读取的有效值，继续按现有缺失、空值和数值校验规则生成 |
| `content_hash` | 继续对原始响应计算；不将沿用字段混入原始响应哈希 |

`canonical_extra_json` 和 `field_provenance_json` 在新结构中取消；它们承载的有效沿用信息合并到 `retained_fields_json`。默认字段来源由行级 `run_id` 表达，不为每个正常字段重复保存一次。

示例：任务 120 返回了一笔融券卖出量，任务 125 对同一交易日的响应漏掉 `RQMCL`：

```json
{
  "RQMCL": {"value": 67900, "run_id": 120}
}
```

该行的 `run_id` 为 125。其余在任务 125 响应中出现的字段，默认来源也是 125。任务 126 重新返回 `RQMCL` 后，移除这条沿用记录，无论新值是否与旧值相同。

这里的来源表示“哪次任务实际取得了该字段”，不是完整的字段修订历史。方案与当前表一样保存当前有效状态，不承诺恢复每次历史响应；逐次响应审计需要另行设计。

## 更新规则

先在事务外解析、校验候选记录，再在 `complete_sync()` 的同一事务中写入事实、成功任务及水位。

对于每个源字段，按“键是否存在”处理，而不是按值的真假处理：

| 新响应情况 | 处理 |
| --- | --- |
| 字段存在且值有效，包括合法的 0、负融资净买入 | 使用新值；移除该字段的旧沿用记录；来源为本次任务 |
| 字段存在且明确为 `null` | 按该字段现有规则处理未知值；可选字段不沿用旧值，移除旧沿用记录；必要字段不满足校验时拒绝提交 |
| 可选字段没有返回，但此前实际取得过 | 保留旧有效值和原始任务编号，写入一条沿用记录，并给出来源缺字段警告 |
| 字段没有返回，此前也没有实际取得过 | 保持未知；不凭空制造沿用值或来源编号 |
| 必要字段缺失、格式无效或股票/日期不匹配 | 拒绝该批提交，保留已保存事实及成功水位 |

必要字段包括当前适配器要求的股票身份、日期和融资余额。对可选数值列，来源键与列名映射继续使用现有 `RZYE/RQYE/RZRQYE/RZJME/SPJ` 规则，零值、负值、显式空值的合法范围保持现有契约。

合并算法：

1. 从旧 `raw_json` 与旧 `retained_fields_json` 重建此前有效源字段。原始响应中的字段优先，沿用字段只应存在于原始响应之外。
2. 新 `raw_json` 只保存这次真实响应。
3. 对新响应缺少而旧有效对象包含的键，复制旧值及其真实任务编号到新的沿用对象。连续多次缺字段也保留最初实际取得该字段的编号，不改成本次任务。
4. 新响应返回的字段自动取消沿用，包括扩展字段和明确返回的 `null`。
5. 解析后的数值列、新原始响应和新沿用对象一并入库。只有验证通过才提交。

有效源对象可按 `{沿用字段的值, 再覆盖当前 raw_json}` 重建，供未来字段扩展和诊断使用。图表继续读数值列，不需重建 JSON，也不改前端。

## 来源残留问题

本次审计还发现：**84 条记录、3,360 个字段来源条目**，字段已存在于当前 `raw_json`，映射却指向旧任务。其中包含 `DATE`、`SCODE` 和扩展指标；这与“当前原始响应来自行级 `run_id`”的契约不一致。

当前写入代码只清除五个已映射数值字段的旧来源覆盖，扩展字段重新出现时仍可能带着旧覆盖写回。新规则对所有重新出现的字段统一取消沿用，可消除这一机制问题。

迁移对这类情况输出审计明细：股票、交易日、字段、旧来源编号、行级来源编号、判定依据。当前原始响应中的值以实际保存的原始响应为依据，迁移后来源使用行级编号；旧来源映射保留在迁移前备份及审计报告中。不能将旧覆盖继续误当成真实沿用，也不能无记录地删除矛盾元数据。

如果缺失字段的来源编号不存在、所属股票/来源/数据集不匹配，或有效值无法重建，视为不可自动迁移的异常，停止迁移并列明记录，不猜测来源。

## 迁移与回滚

结构版本从 3 升到 4，新增迁移；既有 `001`、`002`、`003` 文件及哈希保持原样。

当前迁移框架执行静态 SQL。需要增加只适用于版本 4 的数据转换步骤：由 Python JSON 解析旧字段，再执行表重建；必须与版本登记处于同一迁移事务。正常升级路径和命令行维护路径复用这一步，不能只手工处理当前机器。

使用 Python 转换是为了保留 JSON 的字符串、数字、布尔、数组、对象和显式空值类型，避免字符串替换或 SQL 类型转换误伤数据。新沿用对象采用现有确定性 JSON 编码方式。

迁移流程：

1. **隔离验证**：使用 SQLite Backup API 取得一致副本。在副本完成审计、转换、测试和体积测量，形成可核对的结果。
2. **正式维护**：暂停后台，取得现有实例锁，并用 Backup API 创建专门的迁移前备份。先迁移再运行，避免新旧代码混用同一个库。
3. **事务内重建**：创建新的融资表，逐行转换并保留主键、数值列、原始响应、哈希、时间和行级任务；审计发现不可恢复异常立即回滚。
4. **逐行验证**：确认有效源字段可等价重建，数值列和原始响应不变，沿用字段及来源均可解释。
5. **替换表并恢复约束**：重建现有索引、外键及实际适用的触发器，登记版本 4。执行 `foreign_key_check`、完整性检查和业务来源检查，通过后提交。
6. **空间整理**：迁移事务结束后，在仍持有维护锁时按隔离测量结果执行 `VACUUM`。失败时保留已通过验证的逻辑迁移库，报告文件尚未压缩；不因此回滚已经正确完成的结构迁移。
7. **恢复服务**：启动新版后台，核对融资图和增量同步。结束维护后保持后台运行，便于查看。

迁移和空间整理阶段需要额外磁盘空间，按主库、一致备份、转换临时空间及 `VACUUM` 临时文件核算；以实测余量作为执行条件。备份会保留原体积，节省的主库空间不等于整个数据目录同幅减少。

回滚使用匹配结构版本的旧代码和迁移前备份。先停服务并取得实例锁，通过项目维护/恢复流程验证备份后替换，不对运行中的主库做裸文件覆盖。升级后如果已经新增同步事实，回滚会丢掉备份之后的数据，需先另存升级后数据库供恢复或重新同步。

## 验收条件

| 场景 | 必须验证的结果 |
| --- | --- |
| 正常完整响应 | 沿用对象为 `{}`，只有一份完整原始 JSON |
| 可选数值字段缺失 | 旧数值和原任务编号保留，原始响应不混入旧值 |
| 扩展字段缺失 | 旧扩展值可重建，只有缺失字段进入沿用对象 |
| 字段连续缺失 | 沿用原始任务编号，不反复重写为新任务 |
| 数值/扩展字段重新返回 | 移除旧沿用；相同值、不同值和明确空值均覆盖旧状态 |
| 0、负融资净买入、null、布尔、数组、对象 | 数值契约和 JSON 类型保持正确 |
| 没有历史值的缺字段 | 不生成虚构沿用或来源 |
| 必要字段/已知日期缺失、请求失败 | 事实和成功水位不受失败批次影响 |
| 现有 84 条来源冲突记录 | 审计完整，当前响应内字段使用正确行级来源，数值不变 |
| 不可解释的旧沿用值或任务编号 | 转换失败、事务回滚，主库保持原结构 |
| 中断与再次启动 | 不出现半迁移，重试不会重复转换或重复插入 |
| 服务读取、最近一年展示、30 天回看修订 | 图表数据与同步行为一致 |

迁移快照的硬性核对指标：融资主键集合、记录数、所有数值列、原始 JSON 对象、原始哈希、行级任务编号和时间保持一致；其他业务表的内容不变。对每条记录，重建的有效源对象与旧有效对象等价；来源修正限定于已审计的当前响应内旧覆盖。

性能和空间验收分别报告：JSON 内容总字节、融资表数据页/索引页、数据库文件大小、页内空余、迁移及整理耗时、最近一年查询和普通增量更新耗时。占用有明确下降，展示与更新没有不可接受的退化。

## 实施边界

第一阶段涉及 `financing_daily` 的版本 4 迁移、`ChipService` 的候选合并与写入、`Database.check()` 对沿用字段来源的校验、旧 JSON 导入兼容、相关回归测试和存储说明。

后台刷新频率、30 天回看、前复权版本、财报/估值表结构及页面流程继续使用现有规则。保留同步任务日志，因为沿用字段仍可能引用它们。

压缩原始响应、完整历史修订日志、无变化时跳过 UPSERT、调整页大小或改 journal 模式可作为后续独立议题，不与本次去重迁移捆绑。第一阶段完成后，再根据真实体积和耗时决定是否需要进一步优化。
