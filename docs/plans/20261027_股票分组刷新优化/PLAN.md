# 股票分组刷新优化

状态：已实施、验收并部署；本次补充耗时展示及限速模板修复。实际生产耗时未自动重测，限制见PROGRESS.md。日期：2026-10-27。独立计划；后续实现、缺陷修复和验收均在本目录维护。

## 目标与授权

减少个股分组手动刷新、分组定时和显式多股票刷新的请求量与串行等待，同时保持逐股财务口径、增量水位、修订、校验和失败恢复。用户明确允许不同真实提供方的请求并行发送，限速参数由用户自行配置；本任务不自行提高限速或将分组切换为stock_fast。

用户已要求暂停接口②“人数明细”刷新：生产刷新仅保留F10总人数，旧明细及旧缓存仍可查看。用户已授权按本计划实施；测试通过后按项目规则安全部署8765，限速及定时配置不自动改动。

## 范围

### 1．暂停人数明细刷新

- 停止生产流程对RPT_HOLDERNUM_DET的新请求，涵盖单股手动/全量、首次初始化、分组手动、分组定时及继续失败部分；RPT_F10_EH_HOLDERNUM照常更新。
- 不删除明细/旧缓存/旧sync run或历史来源，不改其人数口径，不将明细伪装成F10；下拉仍可查看已有序列。
- 新工作规划不再创建明细采集分段；恢复历史任务时识别停用接口，明确跳过且不推进其水位，不冒充采集成功。旧完成历史保持原状。
- 本轮不新增明细开关；恢复采集须另行明确授权，避免“可选”配置扩大本次范围。

### 2．不同来源并行发送

- 使用真实提供方sina、tencent、baidu、eastmoney、cninfo作为执行通道；已就绪的不同通道可同时存在实际在途HTTP，不能只是线程并行但网络仍被整次任务串行。
- 每个提供方一个有界工作通道/独立会话，最多五个通道同时工作，未选来源不创建空任务；同源实际并发仍沿用个股能力上限1。同属东财的不同接口、域名和股票共用一个通道及公共预算。
- 继续通过RequestCollector和原collection_provider_state、跨进程来源槽位执行；读取用户在“个股采集”保存的限速，未配置用现有默认。其他模块及单股请求仍参与同源锁/预算/冷却，不拆provider，不私建计时预算。
- 同源限速等待只阻塞自身通道，不能挡住其他已就绪来源；来源拒绝立即停止本轮该通道，冷却期间不重复请求，其他来源按原业务依赖继续。
- Session、collector及线程执行上下文有明确所有者，不跨线程共享可变Session、SQLite连接或ContextVar状态；执行任务时显式传递operation、批次、逐股范围、触发方式及取消回调。
- 只并行依赖已满足的步骤。保留财务先于需要本地报告期的公告判定/估值，以及raw/旧版本等价格依赖；已具备资料的股票可先执行，不能为一只缺资料股票挡住所有其他来源。
- 停止与安全关服可取消排队及限速等待，等待真实在途请求结束；不留下后台线程继续写入，不改变原Scheduler或额外建立常驻调度器。

### 3．合并已验证支持的多股请求

先按股票和数据项调用/提取原有范围决策，再按接口、口径、模式、类别集合、日期范围兼容性分组。不能将组内最新水位用作所有股票起点，也不能因多股合并从增量静默变为全量。

|接口|计划|
|---|---|
|RPT_PCF10_INDUSTRY_CVALUE|按SECUCODE多股请求；按查询主体分别选择行业平均，不能取整份响应第一个平均|
|RPT_F10_EH_HOLDERNUM|代码IN与NOTICE_DATE增量条件；保留原前瞻公告日期边界|
|RPTA_WEB_RZRQ_GGMX|SCODE IN，按原逐股水位前14天重叠；连续性验证及必要补偿逐股保留|
|RPT_SHAREBONUS_DET|公告日与除权日两类分别合并；未实施报告期复查及必要全量补偿单列|
|RPT_F10_FN_MAINOP|所选时按SECUCODE及报告期/日期范围合并，字段/维度及精确来源引用保留|
|巨潮公告|分号连接code,orgId；已有身份、兼容类别及相近尾部范围合并；身份缺失时一次索引匹配多股|
|RPT_HOLDERNUM_DET|停刷，不参与合并|
|新浪四表、百度历史三指标、腾讯历史raw/qfq|继续逐股现有请求；不同提供方可并行，口径不换成实时数据|

- 默认每批最多20只股票，6只仅是既有回归样本，不是生产分块上限。8只、10只、15只等在接口/范围兼容且请求长度、响应规模允许时可归入同一批；超过20只自动分块，股票分组本身无20只人数限制，也无需因新增成员修改代码。
- 批大小归来源适配器的明确参数，不能在编排代码里散落写死；通用默认20，各接口可依据有限验收结果设独立上限。20是本次计划的设计值，不是已证实的来源公开容量；实际启用前须完成相应接口20股完整性验收，未通过的接口记录原因并使用已验证的较小上限。
- 分块同时考虑股票数、URL/POST请求长度、预期响应/分页规模及日期范围兼容性；不能只看股票数。优先通过分页承接正常数据量，确需细分时按明确规则细分；来源拒绝后不拆请求绕过冷却。
- 同一接口内日期略有不同的普通增量可用受控日期并集，回包后按每股原范围过滤，保证结果与逐股等价。跨度明显不同、首次长历史、修订核对或补偿与普通尾部更新分开；实施前将“兼容范围/最大扩展量”变为确定配置或纯规则并记录，不留随意启发式。
- 不依赖尚未验证的“按股票分别绑定日期条件”的OR语法。巨潮全量名单索引无需逐股重复下载，但不把身份获取变成页面读请求。
- 按原接口真实分页能力顺序抓全，检查总数、页长度、跨页重复和边界变化。返回股票代码必须属于固定小组，同股事件/日期去重符合原定义。
- “没有出现某股”不直接等于这只股票成功无数据。只有筛选确实生效、全页完整及无数据语义可证明时才登记零；名单忽略/只返回第一或最后一股、截断、未知缺行需失败或定向核验。

### 4．保留逐股发布、修订及恢复

- 各股原解析、业务比较、有效零/负值、缺失、sync_run、水位及范围约束不变；名单和业务范围在启动时固定，同股同数据项跨组互斥延续。
- 全部分页/名单完整性校验通过后再发布独立可提交的股票结果；整段请求/分页失败不发布不完整数据。允许已通过逐股业务校验的股票短事务提交，单股业务失败不推进其水位。
- 恢复按相同成员/口径/范围只处理失败和未完成部分，复用成功结果；不得重新下载整组已完成历史，不能靠一次新任务重置来源预算。
- 保持metadata_only，不为共享响应新增原文、临时响应片段、BLOB或镜像缓存。

### 5．公共batch/source及统计适配

- 继续使用operation → 真实batch → source。共享多股/范围段是一个真实batch，HTTP分页及重试各自登记source；不能为每股复制同一source，不能增加父子batch层或公共item表。
- scope保存固定的小组名单、必要逐股范围、接口及版本，幂等键包含真实范围和口径。每股sync_run仍独立，通过紧凑引用关联真实分段；来源与事实引用须满足现有同batch约束（特别是主营构成）。
- 现有“每股planned batch”和complete_sync同时结束批次的实现需适配：共享分段不能在第一只股票提交后就被标为整体完成。分开逐股业务提交与共享分段终态责任，不新建假batch凑旧进度。
- 一批内保存有界的逐股状态/计数/run引用，不复制每股全量业务结果/响应；operation只保留必要摘要。实施第一阶段明确字段、状态、引用及恢复判定，优先复用现有表，不预设新增表或迁移。
- 总进度仍按股票×所选业务数据项计算。价格raw/qfq、估值三指标/同行是内部子分段，不改变用户所见业务项数。
- 整组写入汇总=逐股实际已提交计数之和；新增/修订/未变化/未知分开。共享source的实际HTTP只计一次，逐股显示“关联请求”时明确不可相加；源响应行数、分股解析量和派生计数不混算。

### 6．进度与可解释性

- 保留现有整组汇总，增加可展开的每股数据项状态、实际新增/修订/未变化、失败原因及真实更新时间；旧记录缺计数继续显示未知。
- 请求原因细分为增量、分页、历史锚点核验、历史重建、重试及身份辅助，说明请求数为何超过“股票数×接口数”；复权重建记录实际触发原因及涉及日期范围。
- 分开显示实际总耗时、来源在途/等待等有真实记录的时间；不同通道时间可重叠，不把各股/来源耗时相加冒充墙钟总时间。没有记录的旧时长不猜测。
- 本轮保留前复权旧锚点核验及必要历史重建，不新增调整核验频率的配置；是否降低其频率后续单独研究，不能为本次提速静默取消校验。

## 实施阶段

1. **基线与模型定稿**：读取本目录三文件；记录当前Git diff和隔离回归基线；列明每股业务依赖、范围兼容规则、分段字段/状态、逐股sync引用、来源外键与互斥恢复。固定逐股/整组计数口径，确认不需要新表时不做迁移；需要迁移则补DDL/回退和存储说明后实施。
2. **停刷明细与来源并行**：更新所有生产入口/规划；实现有界、独立来源通道及显式依赖，保持共享限速。先用离线假响应证明真实请求重叠和停止/冷却/关服行为。
3. **多股请求与逐股发布**：先同行、F10人数、融资，再分红/主营及巨潮；为每类处理范围、分页、缺股和分流验证。接入共享batch/source、逐股业务提交及失败定向恢复；不将未完成适配混进生产流程。
4. **进度适配**：整组、逐股、来源及请求原因共用真实计数，验证旧历史仍可读；不能因为合并减少batch便减少36个业务工作项或重复计HTTP。
5. **隔离验收**：运行对应来源、领域、公共运行控制、限速/并发、SQLite、HTTP与前端回归；使用隔离数据库、缓存、写目录和假时钟，不修改日常数据。
6. **有限实测与部署**：先有限两股/六股回归，再验证设计默认20股的真实返回、分页和去重；21股以上的分块边界主要用离线响应验证，不扫描或探测来源最大批量/封禁阈值；对比等价范围及同一限速配置下的请求量和耗时。部署前核对宿主机8765身份及活动任务；等待空闲后按项目规则重启，检查日志、原配置和页面，保持原库后台运行。

## 验收与完成标准

- 明细：单股/全量/首次/分组/定时/恢复均无DET新请求，F10仍更新；旧明细和旧缓存继续可读，无历史删除或伪造更新。
- 并行：用同步屏障/假会话证明至少两个不同来源同时在途；同源跨接口/跨任务/进程仍只有1，保存的个股限速生效，单股stock_fast例外不扩张。
- 依赖：缺财务的股票等待相应步骤，已就绪股票不受无关阻塞；停止等待可取消，拒绝后同源不再发送，其他来源按依赖继续，安全关服无遗留写线程。
- 范围与来源：两股/六股/20股及21股以上分块边界、不同水位、首次与旧股混合、日期并集、缺股、空结果、只返回最后一股、分页截断/重复、接口结构变化均有覆盖；不完整响应不发布，不跨股票串写。
- 等价性：原逐股和新批量对相同离线样本的事实、修订、sync状态、水位及覆盖判断一致；同行按查询主体正确选平均，分红各类增量/未实施复查保留。
- 恢复：单股失败不推进该股水位，成功股不重复发布；重复启动、同股跨组、重启恢复及取消保持原约束，预算/冷却不重置。
- 统计：整组总计与逐股已提交值一致；实际source一次计数；一只股票大量修订可定位，旧缺计数仍未知。6股×6类仍36项，停刷详情只减少内部来源分段。
- 性能：分别报告总HTTP、各来源HTTP/分页/补偿/重试、共享预算等待及墙钟总时长；用明确相同名单/范围/限速、是否存在其他任务和源数据变化解释比较。没有可比基线时标明，不能以缓存命中冒充并行收益，不承诺固定分钟数。
- 整组summary展示operation开始至结束的墙钟耗时；运行中显示已运行耗时，历史记录使用真实开始/结束时间。来源合法空结果提示未更新，不单独计为失败；真实请求、解析、发布、存储错误仍按失败保留。
- 个股限速“较快”模板必须明显区别于默认：2秒间隔、最多追加3秒、60秒30次、每20次休息10秒、单并发；该模板需用户主动选取并保存，不改变现有保存配置或共享预算/冷却。
- 文档：实施后同步stock-collection、collection-management、架构导航及实际存储变化；新资料放data/verification对应目录，清理隔离库/测试缓存/预览及一次性脚本，保留证据、报告、常用工具和当前后台日志。

## 本轮不做

不自动改变限速或旧定时配置，不将分组启用stock_fast，不自动切换报告期，不修改财务来源/人数口径，不新增PDF或模型任务，不改其他模块采集策略，不删除历史，不在本计划中调整前复权核验频率，不创建另一个长期测试后台。
